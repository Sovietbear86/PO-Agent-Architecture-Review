# Инструкция для AI-агента по работе со статусной схемой задач AS21

## 1. Назначение

Этот файл задает единые правила интерпретации статусов задач AS21 для:

- анализа спринтов;
- расчета velocity и throughput;
- расчета lead time и cycle time;
- контроля WIP;
- выявления блокировок;
- анализа очередей review и QA;
- определения возвратов на доработку;
- прогнозирования завершения спринта и релиза.

Источник — действующая статусная схема AS21, предоставленная владельцем продукта.

> Важно: на визуальной схеме разрешено много переходов между статусами.  
> Агент не должен пытаться восстановить полную матрицу переходов только по изображению.  
> При наличии API или настроек workflow AS21 именно они считаются источником истины.

---

## 2. Список статусов

| Статус AS21 | Русское значение | Смысл | Аналитическая категория |
|---|---|---|---|
| `Open` | Открыта | Задача создана, но активная работа еще не началась | Backlog |
| `Need info` | Требуется информация | Для продолжения не хватает данных, решения или ответа | Waiting / Blocked |
| `In progress` | В работе | По задаче ведется активная работа | Active Work |
| `Ready for review` | Готово к ревью | Результат подготовлен и ожидает проверки | Review Queue |
| `In review` | На ревью | Выполняется code review, техническое или аналитическое ревью | Review |
| `Ready for QA` | Готово к QA | Реализация готова и ожидает передачи в тестирование | QA Queue |
| `QA` | Тестирование | Выполняется проверка качества или приемка | Testing |
| `Reopened` | Переоткрыта | Задача возвращена на доработку после проверки или завершения | Rework |
| `Resolved` | Решена | Исполнитель считает работу завершенной, но может требоваться финальное закрытие | Done Pending Closure |
| `Closed` | Закрыта | Задача окончательно завершена | Done |
| `Cancelled` | Отменена | Задача исключена из актуального объема работ | Cancelled |

---

## 3. Базовая логика процесса

Типовой маршрут задачи:

```text
Open
→ In progress
→ Ready for review
→ In review
→ Ready for QA
→ QA
→ Resolved
→ Closed
```

Допустимые отклонения:

```text
Open / In progress
→ Need info
→ In progress
```

```text
In review / QA / Resolved / Closed
→ Reopened
→ In progress
```

```text
Любой статус
→ Cancelled
```

Агент не должен считать нетипичный маршрут ошибкой автоматически. Он должен:

1. зафиксировать фактическую последовательность статусов;
2. определить время, проведенное в каждом статусе;
3. выявить возвраты назад;
4. отметить пропущенные этапы;
5. показать возможный риск, но не делать категоричный вывод без контекста.

## 4. Группировка статусов для аналитики

### Backlog

- `Open`

Используется для оценки входящей очереди и задач, еще не взятых в работу.

### Waiting / Blocked

- `Need info`

Время в этом статусе не считается чистым временем активной работы.  
Его нужно учитывать как ожидание или блокировку.

### Active Work

- `In progress`
- `Reopened`

`Reopened` дополнительно считается признаком возврата на доработку.

### Review

- `Ready for review` — очередь на ревью;
- `In review` — фактическое ревью.

Эти статусы нужно считать раздельно, чтобы отличать ожидание от активной проверки.

### QA

- `Ready for QA` — очередь на тестирование;
- `QA` — активное тестирование.

Эти статусы также нужно считать раздельно.

### Completed

- `Resolved`
- `Closed`

`Closed` — окончательное завершение.  
`Resolved` — условное завершение, которое может требовать подтверждения или закрытия.

### Cancelled

- `Cancelled`

Не считается успешно выполненной задачей и не включается в успешный throughput.

## 5. Правила расчета основных метрик

## 5.1. Cycle Time

### Начало

По умолчанию:

```text
первый переход в In progress
```

Если задача стартовала сразу со статуса `In review`, `QA` или `Reopened`, агент должен:

- использовать первый статус из группы Active Work / Review / QA;
- отметить маршрут как нетипичный.

### Окончание

Основной вариант:

```text
первый переход в Closed
```

Допустимый альтернативный вариант:

```text
первый переход в Resolved
```

Альтернативу можно использовать только если для конкретного проекта подтверждено, что `Resolved` фактически означает завершение.

---

## 5.2. Lead Time

По умолчанию:

```text
дата создания задачи
→ первый переход в Closed
```

Если проект использует `Resolved` как окончательное завершение, это должно быть явно указано в конфигурации.

---

## 5.3. WIP

### Базовый WIP

Включать:

- `In progress`;
- `In review`;
- `QA`;
- `Reopened`.

### Расширенный WIP

Дополнительно включать:

- `Ready for review`;
- `Ready for QA`.

При расчете агент обязан указывать, какой вариант WIP использован.

---

## 5.4. Blocked Time

В blocked time включать:

- время в `Need info`;
- время с установленным признаком блокировки, если такой признак существует в AS21.

Агент должен отдельно показывать:

- длительность блокировки;
- причину;
- внешнюю зависимость;
- автора последнего запроса информации.

---

## 5.5. Review Time

Разделять:

```text
Review Queue Time = время в Ready for review
```

```text
Active Review Time = время в In review
```

Если очередь существенно больше фактического ревью, это признак bottleneck.

---

## 5.6. QA Time

Разделять:

```text
QA Queue Time = время в Ready for QA
```

```text
Active QA Time = время в QA
```

Если задачи долго находятся в `Ready for QA`, агент должен проверять загрузку QA и наличие тестовой среды.

---

## 5.7. Throughput

По умолчанию:

```text
количество задач, впервые перешедших в Closed за период
```

Не включать:

- `Cancelled`;
- повторные переходы одной и той же задачи в `Closed`.

Если проект считает завершением `Resolved`, это должно быть задано отдельно.

---

## 5.8. Reopen Rate

```text
Reopen Rate =
количество задач, которые хотя бы один раз переходили в Reopened
/
количество завершенных задач
```

Дополнительно считать:

- среднее число переоткрытий;
- долю времени после первого `Reopened`;
- этап, с которого чаще всего происходил возврат.

---

## 5.9. Carryover

Задача считается перенесенной, если:

- она входила в committed scope спринта;
- к концу спринта не находилась в `Resolved`, `Closed` или `Cancelled`.

`Cancelled` показывается отдельно и не считается успешно выполненной задачей.

---

## 6. Сигналы и риски

Агент должен автоматически обращать внимание на следующие ситуации.

### Длительное ожидание информации

```text
Need info дольше установленного порога
```

Рекомендация: определить владельца ответа и дату следующей контрольной точки.

### Очередь на ревью

```text
Ready for review растет быстрее, чем In review
```

Рекомендация: проверить загрузку ревьюеров и WIP-limit.

### Длительное ревью

```text
In review дольше нормы
```

Рекомендация: проверить сложность изменения, доступность эксперта и наличие замечаний.

### Очередь QA

```text
Ready for QA дольше нормы
```

Рекомендация: проверить доступность QA, среды и тестовых данных.

### Длительное тестирование

```text
QA дольше нормы
```

Рекомендация: проверить дефекты, нестабильность стенда и полноту критериев приемки.

### Переоткрытие

```text
переход в Reopened
```

Рекомендация: определить причину — дефект, неполная постановка, ошибка реализации или изменение требований.

### Зависание между Resolved и Closed

```text
Resolved без перехода в Closed дольше порога
```

Рекомендация: проверить, требуется ли приемка, подтверждение заказчика или формальное закрытие.

### Отмена после начала работ

```text
In progress / Review / QA → Cancelled
```

Рекомендация: посчитать потраченные усилия и причину исключения задачи.

## 7. Ответы на типовые вопросы

### «Какие задачи сейчас в работе?»

Показывать:

- `In progress`;
- `In review`;
- `QA`;
- `Reopened`.

Отдельно показывать очереди:

- `Ready for review`;
- `Ready for QA`.

### «Какие задачи заблокированы?»

Показывать:

- `Need info`;
- задачи с отдельным признаком блокировки.

### «Какие задачи завершены?»

Разделять:

- `Resolved` — решены, но могут ожидать закрытия;
- `Closed` — окончательно завершены.

### «Какие задачи не вошли в поставку?»

Показывать:

- `Cancelled`;
- незавершенные задачи спринта;
- задачи в `Resolved`, если политика релиза требует `Closed`.

### «Где bottleneck?»

Сравнивать:

- время в `Ready for review` и `In review`;
- время в `Ready for QA` и `QA`;
- время в `Need info`;
- частоту `Reopened`.

---

## 8. Правила для неизвестных статусов

Если агент получает статус, которого нет в этом файле:

1. не отбрасывать задачу;
2. нормализовать значение;
3. отнести к категории `Unknown`;
4. не включать автоматически в WIP или Done;
5. показать предупреждение о качестве данных;
6. предложить добавить статус в конфигурацию.

Пример:

```text
Обнаружен неизвестный статус: "Waiting for deployment".
Он не учтен в текущей аналитической модели.
```

## 9. Рекомендуемая машинно-читаемая конфигурация

Для кода агента рекомендуется использовать отдельный файл:

```text
config/workflow_statuses.yaml
```

Ключевые параметры:

```yaml
cycle_time:
  start_status: "In progress"
  default_end_status: "Closed"
  optional_end_status: "Resolved"

analytics:
  basic_wip_statuses:
    - "In progress"
    - "In review"
    - "QA"
    - "Reopened"

  waiting_statuses:
    - "Need info"

  completion_statuses:
    - "Resolved"
    - "Closed"

  successful_throughput_statuses:
    - "Closed"

  excluded_from_successful_throughput:
    - "Cancelled"
```

Списки статусов не следует хардкодить в промптах или исходном коде.

---

## 10. Ограничения

- По изображению нельзя надежно восстановить все допустимые переходы.
- В разных проектах AS21 смысл `Resolved` может отличаться.
- Агент обязан использовать историю изменений, а не только текущий статус.
- Для корректного анализа спринта требуется дата начала и окончания спринта.
- Для расчета predictability нужен committed scope на момент старта.
- Полная матрица переходов должна поступать из API или настроек workflow AS21.
